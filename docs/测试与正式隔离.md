# 同一云环境：测试与正式分区

云环境固定为 `cloud1-d2glj4fu92e8f1497`。微信客户端版本自动决定调用目标，不提供页面切换开关。

| 客户端版本 | 分区 | 业务函数 | 定时任务 |
|---|---|---|---|
| 开发版 `develop` | test | `coach_test` | `reminderJob_test` |
| 体验版 `trial` | prod | `coach_prod` | `reminderJob_prod` |
| 正式版 `release` | prod | `coach_prod` | `reminderJob_prod` |

版本不可识别时停止云端请求；服务响应中的 `stage` 不匹配时拒绝处理数据。版本路由不作为访问权限凭据，服务端继续依靠微信身份、归属和付费状态校验。

## 数据、缓存与素材

| 资源 | test | prod |
|---|---|---|
| 账号快照 | `coach_test_accounts` | `coach_accounts` |
| 订单索引 | `coach_test_order_index` | `coach_order_index` |
| 本机数据 | `coach:test:<owner>` | `coach:prod:<owner>` |
| 本机账号指针 | `coach:test:owner` | `coach:prod:owner` |
| 新素材目录 | `test/` | `prod/` |
| 新订单 | `bjt` + 24 位十六进制字符 | `bjp` + 24 位十六进制字符 |

四个集合均禁止客户端直接读写。正式集合名称和账号文档 ID 保持原样，无需迁移既有云端数据。

每个本机快照包含训练会话、评估草稿、待同步操作、冲突、游标和启动时间，因此这些状态一并按分区隔离。体验版与正式版共享 prod 快照。旧 `coach:owner`、`coach:<owner>` 缓存保留，不自动读取、删除或上传；需要恢复旧未同步记录时先核对来源，再单独安排迁移。

`server/stages.json` 是分区配置来源；生成器为小程序生成 `miniprogram/shared/stages.js`，为 Node.js 云函数保留 JSON 配置。小程序前端只通过 JS 模块加载配置，不直接 require JSON。新增视频按所属 `storagePrefix` 上传，并分别配置该分区的 `EXERCISE_MEDIA`。已有正式计划和素材引用不自动重写。bootstrap 也返回当前分区的素材目录。应用没有新增上传接口。

## 源码与部署包

业务源码统一放在 `server/entries/`，公共业务和运行时在 `server/`，领域逻辑在 `shared/domain.js`。

```sh
npm run prepare:cloud
npm run release:check
npm test
```

生成器生成五个部署入口及 `deployment.json`。每个包固定自身分区，客户端不能覆盖；所有包具有相同 `sourceVersion` 内容哈希。`check` 对比入口、共享模块、配置及哈希，禁止部署陈旧生成包。不要直接编辑 `cloudfunctions/*/lib` 或生成的入口。

业务接口统一返回 `{stage, sourceVersion, code, data?, message?}`；定时任务也返回分区标识。HTTP 支付回调保留平台所需的 `success` 应答，通过 `X-Coach-Stage` 与 `X-Coach-Version` 响应头标识分区和版本。

## 显式选择部署目标

先查看计划；`--dry-run` 不生成文件、不连接微信、不上传函数：

```sh
sh uploadCloudFunction.sh test --dry-run
sh uploadCloudFunction.sh prod --dry-run
sh uploadCloudFunction.sh callback --dry-run
```

实际部署前设置 `WECHAT_DEVTOOLS_CLI` 为本机官方 CLI 的绝对路径，然后选择唯一目标：

```sh
sh uploadCloudFunction.sh test
sh uploadCloudFunction.sh prod
sh uploadCloudFunction.sh callback
```

- `test` 只上传 `coach_test` 和 `reminderJob_test`。
- `prod` 只上传 `coach_prod` 和 `reminderJob_prod`。
- `callback` 只上传 `paymentCallback`。
- 无参数或未知目标直接退出。设置的 `WECHAT_CLOUD_ENV` 与固定环境不一致时也退出。
- 正式部署使用与测试验收相同的源码版本，记录 `deployment.json` 的 `sourceVersion`。
- 此脚本不自动修改后台环境变量、数据库权限、HTTP 接入或订阅模板，也不自动停用旧触发器。

## 支付：两边都允许真实扣款

测试分区不是模拟支付，也不是微信沙箱。两个分区都使用真实虚拟支付 `env=0`、单轮 990 分，均须满足支付开通及内容发布条件。可以配置同一已批准商品；新订单保存各自下单时的商品 ID，签名和回调都使用该订单商品。

分别在两个业务函数与对应定时任务配置支付参数、内容、订阅模板及相关开关；两组权益签名密钥分别设置。AppID 下的支付凭据和订阅能力本身可能共享，不因业务分区而获得独立平台额度。

共享 `paymentCallback` 配置实际 AppID、Token、EncodingAESKey，并作为微信加密 JSON 消息推送入口。先验签、解密、验证 AppID，再严格按订单格式选择唯一分区：

- `bjt` + 24 位小写十六进制字符 → test。
- `bjp` + 24 位小写十六进制字符 → prod。
- 旧 `bj` + 24 位小写十六进制字符 → prod。
- 未知格式、订单不存在、用户或商品不匹配 → 拒绝处理，不搜索其他集合。

回调在所属集合中处理发货、重复通知、退款和投诉；查询补发也只扫描所属分区。旧订单没有 `productId` 时，使用回调原有 `PAY_PRODUCT_ID` 校验；旧订单未全部处理完前保留该配置，不随新商品任意修改。

## 推送与任务

两个任务使用独立触发器名，每 5 分钟运行，分别处理所属分区的待支付订单、任务完成状态、授权状态及消息去重。

- test 消息固定 `miniprogram_state=developer`，忽略 `MESSAGE_STATE` 的覆盖。
- prod 默认 `formal`；首发前可设置 `MESSAGE_STATE=trial`，发布后切回 `formal` 或删除该覆盖。
- prod 配置为其他值时停止任务并报错，不能把正式提醒误发到开发版。
- 同一账号在两套挑战中可能分别收到一条消息；“每天最多一次”在各分区内部执行。
- 业务分区不隔离微信 AppID 下的平台订阅授权额度，发送仍以微信接口结果为准。

## 首次切换与回退

1. 检查现有云函数、订单和定时触发器。保留正式集合及旧订单。
2. 创建两个测试集合，确认四个集合客户端权限关闭；完成五个函数的环境变量与模板配置。
3. 单独部署共享回调并验证旧 prod 订单兼容，再开始新前缀订单联调。
4. 部署 test；使用开发版验证支付、回调、首训、记录、退款和开发版提醒。
5. 停用旧无后缀 `reminderJob` 触发器，再部署同一源码版本的 prod；体验版连接 prod 验收。旧 `coach` 不再由脚本部署，先确认旧客户端使用情况，再停用其新订单入口，避免遗漏旧调用方。
6. 发布小程序，prod 的消息落点切回 formal。按 `sourceVersion` 留存各部署产物和配置记录。

回退只恢复指定分区的旧代码与环境变量，不覆盖另一个分区，不删除数据。共享回调如需回退，必须保留两种新前缀和旧 bj 订单识别，不能退回只识别旧订单的版本。出现收款异常时关闭对应分区的 `PAYMENT_READY`；暂停提醒则停用对应触发器。

## 验证范围

自动化覆盖版本路由、未知版本、错分区响应、请求中切换版本、完整缓存隔离、相同微信账号的订单与权益隔离、恶意分区参数、旧正式订单、回调幂等与退款、独立定时任务及部署命令的目标限制。

云端部署、真实平台通知、真机付款退款及微信版本跳转仍需实际联调，自动化夹具不产生真实付款和消息。
