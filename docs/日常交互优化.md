# 日常交互优化

本轮保留首次评估、套餐、原生三栏导航和原有训练执行流程。当前代码和云函数包已更新，发布仍按项目原有测试／正式分区流程进行。

## 用户路径

- 今日：默认展示当前时段的一餐建议；记录按钮明确餐次，只记录这一餐。已有内容会询问补充或替换。
- 统一入口：文字、拍照与快捷调整在今日页底部面板完成。明确的实际进食直接记录，未知餐次只补问一次。准备吃、否定、疑问、其他日期的表达不会自动写成今天的摄入。
- 混合输入：例如“午饭吃了面，晚上只有十五分钟”，记录和调整分别处理；调整失败不撤回已保存的记录，重试不重复追加。
- 图片：主动告知和同意后自动识别；同一面板编辑、选择餐次、确认。识别失败仍保留本机照片并允许文字记录。图片和原始身体信息不进入使用统计。
- 当天调整：展示具体方案，点击采用后用于当天训练或对应餐食。恢复之前安排不会覆盖周计划或已完成的训练；正在训练时先结束并保存实际进度。
- 成长：本周摘要置顶，只补问缺少的复评反馈。至少两次有效训练反馈才推导训练难度；疲劳／饥饿感使用明确的本周反馈，或至少两个日期的一致记录。跳过不创建默认评价。
- 长期偏好：先确认保存，可在“我的”移除；AI 问答携带有效偏好。存在未经核验的饮食限制时，不自动提供具体食材替换。

## 数据与接口

`shared/daily.js` 是客户端和云端共享的确定性理解、记录投影与回顾规则。清晰的常见表达不需要调用模型或消耗额度；一般问题通过原有 AI 指导服务回答，沿用授权、成功次数计费与重试机制。

新增记录：

- `meal:{planId}:{date}:{slot}`：早餐、午餐、晚餐、独立加餐。保存内容、来源、上次内容与时间。编辑和撤销都是有版本的同步写入；空内容用于清除，不复活旧三餐文字。
- `feedback:{planId}:{date}`：实际疲劳、饥饿感和反馈时间范围。
- `preference:{id}`：用户确认的偏好；移除后保留非激活状态供同步。
- `override:{planId}:{date}:{target}`：只能通过云端当天调整接口写入。目标为 workout 或具体餐次。

接口 `day.propose`、`day.adopt`、`day.undo` 接收 `requestId`、`planId`、`date`、`baseVersion`；采用及撤销另需 `proposalId` 和 `overrideVersion`。服务端校验有效计划、会员权限、日期、周版本、当天覆盖版本与已完成训练。相同请求标识复用结果，改用相同标识提交不同内容会被拒绝。

训练保存 `adjustmentId`，服务端按真正采用过的对应方案校验组数；原有训练继续按原周计划校验。当天提议与操作账本不在公开状态中返回，删除个人数据会一并清除。账户沿用现有容量限制，不静默丢弃历史操作。

新旧饮食数据共同可读；新逐餐记录优先于旧的同餐文字。饮食任务完成状态仍使用原有 daily 字段，不根据进食文字推断。离线写入与冲突继续使用现有队列及“我的”版本选择入口。

## 验证与统计

运行 `npm run prepare:cloud`、`npm run check`、`npm test`。新增测试覆盖逐餐撤销、餐次补问、多餐及混合输入、否定及未来表达、照片失败和确认、离线重试、丢失响应、当天版本冲突、替代方案真实执行及可跳过反馈。

使用事件仅保留名称、时间、日期及可选交互耗时 `durationMs`：`meal_record_started` / `meal_recorded` 用于记录完成率；`meal_edited` / `photo_corrected` 用于纠正率；`adjustment_proposed` / `adjustment_adopted` / `adjustment_undone` 用于调整采用与撤销；`daily_detail_opened` 用于详情跳转。不得加入餐食正文、照片、偏好或身体数据。

发布前在微信真机验证小屏与键盘、拍照授权、相册选择、网络切换和原生 tabBar；当前自动检查可验证 WXML/WXSS 编译，不能代替真机视觉检查。无需数据库迁移，新字段按需创建；需同时发布新云函数与小程序前端，旧前端可继续读取原始周计划与旧字段。
