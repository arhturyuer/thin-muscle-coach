# 自然周食谱与餐照

食谱以北京时间自然周归档。有效会员完成适用评测并同意新版说明后，在付款确认、评测同步、饮食目标生效变化和新周首次联网打开时检查方案。只生成今天至周日，已过去的日期和实际餐食保留。目标和摄入分开计算；同一日两页使用同一份饮食展示数据。

- `meal.plan.consent` 保存版本 1 的授权。旧用户可在评测页补同意，旧本机授权不会触发周食谱。新评测在同步时随评测记录提交。调用前仍须满足现有 AI、付费、评测适用范围和定量目标规则。
- `meal.plan.ensure` 使用每周生成锁，同周同版本复用。更新在事务内复验当前账号、评测及目标、日期和有效会员。历史通过 `meal.plan.get` 读取，旧单日食谱仍可显示。
- `meal.photo.save` 验证账号、数据代次、餐别、记录版本及上传内容。先将压缩照片写入云存储，再在事务内一起保存餐食、营养和照片引用。重试复用请求标识；失败时保留草稿。照片按同一账号的有效餐次引用，由 `meal.photo.get` 返回，客户端不收到永久地址或云存储凭据。撤销的上一个版本可恢复；过期、已失去引用以及个人数据删除后的照片由现有提醒任务清理。测试和正式分区分别使用 `test/meal-photos/`、`prod/meal-photos/`。原有本机照片不会自动上传。

## 测试分区接入

2026-11-05，获授权后将共享存储桶从 `PRIVATE` 切换为 `CUSTOM`。生效表达式见 [测试餐照存储规则](../.cloudbase/meal-photo-storage-rules.test.json)。CloudBase 不支持对路径匹配结果取反，因此规则使用正向正则匹配测试餐照目录之外的路径，再判断文件创建者。服务端经可信 OPENID 查询并验证引用，使用管理员 SDK 访问照片。[CloudBase 官方文档](https://docs.cloudbase.net/storage/security-rules) 说明了表达式限制。

`coach_test` 版本 `9b804a5d85df9c41` 已开启 `MEAL_PHOTO_STORAGE_READY`。开发版用合成文件确认客户端无法直接读取和上传测试餐照，测试头像仍可上传和读取。接口拒绝了无关联照片读取、冒用账号读取和未经确认的保存请求。合成文件已清理。真实餐照保存和跨设备读取仍需真机联调。

以下步骤用于重新接入或回滚后的验收。

1. 备份桶的现行权限。仅在获准做测试联调后应用候选规则。保存权限后先确认使用客户端 SDK 直接读取和写入测试餐照路径均被拒绝，已有头像的选取、保存与显示正常。
2. 更新 `coach_test` 和 `reminderJob_test` 的代码，保留现有运行时、触发器和环境变量；规则验收后才给 `coach_test` 设置 `MEAL_PHOTO_STORAGE_READY=true`。照片就绪开关未设置时，仍可使用周食谱及文字记录。开发版走测试分区，正式函数和付款回调无需更新。
3. 用已付测试账号完成新版评测，在真实设备验证当天到周日生成、失败重试及目标更新。确认保存两张餐照后，用同一账号的另一台设备查看；换第二个账号验证拒绝。再验证撤销、换图、删除个人数据和对象清理。先使用专用测试账号，避免改动已有真实记录。
4. 发现问题可先移除 `MEAL_PHOTO_STORAGE_READY`，保持私有规则并保留已有数据；照片排查完成后再启用。

本地验证：`npm run prepare:cloud`、`npm test`、`npm run check`。模拟器使用临时页面数据验证夹板、固定日历、标题一行、安排逻辑两行、日期切换以及其他日期不能拍照。自动化中的两个账号和两个客户端为隔离替身，真实双设备验收须在测试分区配置完成后执行。
